# Contributing to V

Thank you for your interest in V (formerly VOZ), a local-first voice tool.
This document summarizes the workflow the repository actually uses, so that an
outside contribution follows the same rules as the maintainers and the AI
agents that already work here.

> **Project status:** V has no public release yet and no formal process for
> accepting external contributions. The GitHub repository is private. This
> guide describes the workflow planned for when the project opens up (see
> section 16 of [ROADMAP.md](ROADMAP.md)). If you have collaborator access
> today, follow it anyway: it is the same one the maintainers use.

## Naming note

The product is now called **V** and the repository is
`MarshallGomez1103/V`. Internal identifiers keep the old name on purpose: the
Python package is `voz`, environment variables are `VOZ_*`, and user data lives
in `voz/` XDG directories. See [ADR-0009](docs/adr/0009-rename-to-v.md). Do
not rename them as part of an unrelated change.

The command available today is `voz` (for example `uv run voz --no-browser`).
A `v` alias is planned.

## 1. Before writing code

1. Read [AGENTS.md](AGENTS.md) in full. It holds the architecture, privacy,
   scope and definition-of-done rules that apply to every change, whether
   written by a human or generated by an agent.
2. Read [ROADMAP.md](ROADMAP.md), especially the "Convenciones" section and
   the numbered section that matches what you want to work on.
3. Read the relevant [ADRs](docs/adr/). A durable architectural change needs a
   new or updated ADR, not just a discussion in the pull request.
4. If `.ai/HANDOFF.md` exists in your checkout, read it: it may describe work
   in progress that is not yet reflected in `ROADMAP.md`. That file is private
   and transient; it is not versioned and must not be referenced from public
   documentation.

## 2. Pick and register an assignment

- Pick **one to three IDs** from the roadmap that form a single related
  vertical slice. Do not mix unrelated sections in one assignment, and do not
  change more than one vertical slice per task.
- Before implementing, record the assignment in the "Trabajo activo" (active
  work) table of the matching section of `ROADMAP.md`, with the exact IDs and
  the status `en curso` (in progress). Nobody else should be working on the same
  IDs at the same time.
- Update the checkbox, the row status and the latest verified achievement **in
  the same edit**, only after you have verified the result. Code that was
  written but not checked stays pending.
- Keep changes small. Do not rewrite a whole module when a small change is
  enough, and preserve unrelated local changes.

## 3. Verification commands

Run the checks that match the layers you touched. These are the exact
commands from [AGENTS.md](AGENTS.md).

### Backend and CLI

```bash
uv sync --all-groups
uv run voz --no-browser
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run pyright
```

Run a single backend test while iterating:

```bash
uv run pytest tests/unit/path/to/test_file.py -q
```

### Frontend

```bash
cd apps/web
npm ci
npm run dev
npm run lint
npm run typecheck
npm run test
npm run build
```

Do not install Whisper or download speech models, do not call paid providers,
do not publish a package, do not push commits that are not yours, and do not
alter the host operating system as part of ordinary verification.

## 4. Tests

- New behavior needs tests at the appropriate level (unit, integration, or
  frontend).
- Every bug you fix needs a regression test that fails before the fix.
- Cover failure and cancellation paths when your change introduces them.
- Tests must run offline and must not need real models or real recordings.

## 5. Privacy and excluded content

Never include any of the following in a commit or pull request:

- recordings, audio, video or transcripts that are private, yours or anyone
  else's;
- downloaded ASR, diarization or voice models, or their weights (models do not
  belong in Git);
- media files generated during manual testing;
- SQLite databases, caches, or anything under the runtime XDG paths;
- API keys, tokens, `.env` files or any other secret;
- the contents of `.ai/` (local, transient agent session context).

If you need an audio fixture, generate a synthetic one (for example with
`ffmpeg -f lavfi`) and record its provenance and license in
[docs/fixtures-licenses.md](docs/fixtures-licenses.md). Do not use real
recordings.

## 6. Architecture rules in short

The full list is in [AGENTS.md](AGENTS.md). The ones contributors trip over
most often:

- Dependencies point inward: `interfaces/infrastructure -> application ->
  domain`. The domain imports no framework.
- Every external provider sits behind a port; adapters are wired only at the
  composition root.
- The server binds to `127.0.0.1` by default, and nothing calls a cloud API
  unless the user explicitly selected that provider.
- The browser never receives absolute host paths. Errors use stable codes and
  user-safe messages.
- Do not add a dependency without documenting why the standard library and the
  existing dependencies are not enough.

## 7. Documentation language

Public documentation (README, docs, ADRs, issue and pull request templates,
CHANGELOG entries from now on) is written in English. Historical text that
mentions VOZ keeps the old name. User interface strings go through the i18n
catalogs (Spanish and English), not hard-coded text.

## 8. ADRs for durable changes

If your change introduces or modifies a durable architectural decision (layer
boundaries, framework choice, persistence schema, a provider contract, and so
on), add a new ADR in `docs/adr/` or update the existing one, following the
format of the current ADRs (context, decision, consequences, alternatives
considered, verification). Do not record a durable decision only in the pull
request description.

## 9. Commit style

Use `type(scope): summary`, lowercase and in the imperative mood, for example:

```text
feat(asr): add a quality profile for faster-whisper
fix(media-storage): prevent traversal in unsafe file names
docs(adr): complete the providers ADR
test(jobs): cover cancellation during resume
```

Suggested types: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`.
The scope is the affected module or layer (for example `domain`,
`media-storage`, `jobs`, `frontend`, `adr`, `roadmap`).

## 10. Definition of done

A roadmap ID is done only when all of the following hold:

- the smallest complete behavior of the chosen slice is implemented;
- the new behavior has tests at the appropriate level;
- every fixed bug has a regression test;
- formatting, lint, type checking and the relevant tests pass;
- failure and cancellation paths are covered where the change introduces them;
- user-visible behavior and architecture changes are documented;
- the result was verified by running the commands above, not inferred from
  generated files;
- `ROADMAP.md` is updated only after verification, in the same edit as the
  assignment status and the achievement.

Never mark an ID complete because the code was written but not checked. If a
check cannot run, leave the ID pending and record the blocker in the assignment
row.

## 11. Pull requests

Use the repository's pull request template
([.github/pull_request_template.md](.github/pull_request_template.md)) and
complete its checklist: the roadmap IDs touched, the commands you ran, the
absence of secrets, media and `.ai/`, an ADR if applicable, a regression test
if you fixed a bug, and the `ROADMAP.md` update in the same edit.

## 12. Reporting problems

Use the issue templates in [.github/ISSUE_TEMPLATE](.github/ISSUE_TEMPLATE)
for bugs and feature requests. For a security vulnerability, follow
[SECURITY.md](SECURITY.md) instead of opening a public issue.
